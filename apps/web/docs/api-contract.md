# Контракт API для фронтенда: вопросы бэкенду

Типы ответов генерируются из контрактов (`npm run gen:api` → `src/api/generated/`): `packages/contracts/openapi/api.yaml` (services/api) и `services/simulation/docs/openapi.json`. Ответы переводятся в модель экрана мапперами `src/api/mappers/*` с проверкой обязательных полей (`ContractError`). Пока сервисы — моки на фикстурах в форме этих ответов; чего в API нет, мок хранит рядом и помечает.

Статусы: `open` — ждём ответа; `answered` — ответ получен, фронт обновлён.

С `VITE_SERVICES=api` сервисы ходят в services/api (`src/services/api`); чего в API нет, отвечает мок. Проверка на живом api —
`API_SMOKE_URL=http://localhost:8000 npx vitest run src/services/api/live.test.ts` (с `API_SMOKE_SIMULATION=1` — и прогон симуляции).

**Как закрыты вопросы**

- 1 — `required` проставлен у новых схем (`ResultSummary`, `SimulationRun`, `Fleet`); у прежних обязательность по-прежнему проверяют мапперы.
- 2, 15 — отдельного эндпоинта итога нет и не нужно: итог собирается из `GET /projects/{id}/evaluation` и снимка; реестр условий — допущения расчёта (`details.assumptions`), база без `details` — ФОТ задачи. Выбранный сценарий — `inputs.economics`, КП — `POST /projects/{id}/quote-request` (`quoteRequestedAt`, и у сохранённой оценки).
- 3, 12 — правило D-89 остаётся на фронте; `evaluate` переносит выбор на новый расчёт, если вариант снова посчитан.
- 4 — `project.inputs` (модель экрана как есть) и `project.step`; `PATCH /projects/{id}` принимает `inputs`, `step`, `taskId`.
- 5, 8 — `Project.resultSummary` при сохранении; сценарий без окупаемости фронт сохранить не даёт, как и раньше.
- 6 — формат трасс в `openapi.json` по-прежнему «массив объектов»: схему опишет services/simulation; проверка — `trace.ts`.
- 10 — шаг 1 собирается из снимка, `GET /locations/{id}`, `/tasks` и `/facility-types/{code}/parameters`; параметры площадки `site_*` в API пока не хранятся — «нет данных».
- 11 — `POST /projects/{id}/evaluate` принимает `calcOverrides`, `Evaluation.calcDefaults` — исходные значения.
- 13, 14 — прогон через оркестратор: `POST /projects/{id}/simulation-runs` (`fleet`, `conditions` в модели экрана), `GET/DELETE /simulation-runs/{id}`, `…/result`, `…/traces`. Запись прогона в решения проекта — фронт (`inputs.simulation.runId`).
