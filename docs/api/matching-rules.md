# Алгоритм подбора: класс операции и жёсткие проверки

Реализация — пакет `services/api/internal/matching`, версия правил `match-rules/v1` сохраняется в каждом прогоне. Подбор отвечает на вопрос «какие роботы физически могут выполнить эту задачу на этой локации и почему». Ранжирование, число роботов и экономику считают следующие модули (ТЗ 3.4.5, 3.5).

## Шаг 1. Кандидаты по классу операции

Кандидат — активный робот каталога (`solution.kind = robot`, `is_active`), у которого есть активная строка `robot_capability` с классом операции задачи (`task.work_type_id`, скопирован из процесса). Отрасль каталога, тип объекта, подтип и свободный текст на отбор не влияют (PRD 4.1).

Робот без такой строки кандидатом не считается и в «исключённые» не попадает: он не про эту работу (PRD 16.1). Исключение — решения, добавленные в проект вручную (ТЗ 3.4.4), и решение, закреплённое кнопкой «Проверить на своём объекте»: они проходят все проверки, включая проверку класса, и помечаются `isManual`.

## Шаг 2. Условия задачи

Условия берутся из задачи на момент снимка проекта (для `match-preview` — из текущей задачи) и могут быть изменены в проекте (`PUT /projects/{id}/conditions`). У каждого условия указан источник: `task`, `formula`, `project` или `rule`.

| Условие | Откуда | Когда не применяется |
|---|---|---|
| Способ обработки груза | допустимые способы задачи | — |
| Среда | `environment` задачи: indoor или outdoor | — |
| Грузоподъёмность не меньше | `unitMassKg`, если груз неделим | задача без груза (способы только `brushes`/`none`) |
| Ширина робота не больше | `minAisleWidthM − widthClearanceM` (формула) | — |
| Мин. температура | `minOperatingTempC` задачи | — |
| Высота подъёма не меньше | `requiredLiftHeightMm` | если не задана |
| Цена в каталоге | правило подбора | — |

Все числа — поля задачи, видимые и редактируемые на форме; скрытых коэффициентов нет (ТЗ 3.5.1). Запас по ширине (0,6 м для склада, 0,9 м для медучреждения) и температура отапливаемого здания — допущения процесса, подписанные в форме.

## Шаг 3. Жёсткие проверки

Значение робота берётся из строки «робот × класс», а если там пусто — из общих ТТХ робота (`robot_spec`). Для каждой проверки сохраняются значение робота, требуемое значение, единица, источники обоих и сообщение на русском.

| Код | Проверка | pass | fail | unknown |
|---|---|---|---|---|
| `work_type` | класс операции | есть строка класса | нет строки (только для ручных) | — |
| `handling` | способ обработки ∈ допустимые | способ в списке | способ не в списке | способ робота или задачи не указан |
| `environment` | среда | среда робота `both` или равна среде задачи | робот только для улицы или только для помещений | допуски робота не указаны |
| `payload` | грузоподъёмность ≥ массы | достаточно; или груз делимый | меньше массы неделимого груза | грузоподъёмность не указана |
| `aisle_width` | ширина робота ≤ проход − запас | помещается | шире допустимого | ширина робота или проход не указаны |
| `min_temperature` | мин. температура робота ≤ температуры зоны | робот работает при этой температуре | зона холоднее допуска робота | температура не указана |
| `lift_height` | высота подъёма ≥ требуемой | достаточно | ниже требуемой | высота робота не указана |
| `price` | есть цена в рублях | цена по умолчанию есть | цены нет — экономику не посчитать | — |

Проверки со статусом `not_applicable` на итог не влияют.

## Шаг 4. Итоговое состояние

1. Хотя бы один `fail` → **`excluded`**: «Исключено: …» с перечнем нарушений и чисел, например «Грузоподъёмность: нужно ≥ 800 кг, есть 600 кг».
2. Иначе хотя бы один `unknown` → **`needs_verification`**: «Требует проверки: не хватает данных — …». Недостаток данных — не отказ (ТЗ 3.4.3).
3. Иначе → **`passed`**: все жёсткие проверки пройдены.

Порядок в ответе: passed, needs_verification, excluded; внутри состояния ручные кандидаты последними, затем по названию.

## Риски и метки

Риски не меняют состояние, но показываются рядом с кандидатом и попадают в отчёт:

- `specs_unconfirmed` — ТТХ не подтверждены (`specs_confirmed ≠ yes`);
- `throughput_unknown` — производительность класса не указана или не точная (диапазон, аналог);
- `hypothesis_only` и метка `P3` — статус `rnd` или УГТ ниже 7: только гипотеза, не рекомендация (PRD 16.5).

Метки P0–P2 (перенос между отраслями) пока не считаются: для них нужна таблица соответствия отраслей каталога и типов объектов.

## Пример: РЦ Химки, «Перемещение паллет», OP-01

Условия: вилы или платформа, помещение, груз 800 кг неделим, ширина робота ≤ 2,8 − 0,6 = 2,2 м, от 5 °C, цена обязательна.

| Решение | Состояние | Причина |
|---|---|---|
| AMR 800, AMR 1500, Ronavi H1500, Ronavi M, DMR Carrier P, AK-2000-2 | passed | все проверки пройдены (у части ТТХ не подтверждены — риск) |
| Ronavi H2000, DMR 1200, Сёмабот, Робот-штабелёр RoboCV | needs_verification | нет габаритов и температурного диапазона |
| AMR 100, DMR 600, Ronavi RCM | excluded | грузоподъёмность меньше 800 кг |
| Беспилотный тягач Cognitive Pilot, EVOCARGO N1, Робот-тягач RoboCV | excluded | способ обработки (буксировка, кузов), уличные — ещё и среда |
| MARK 2 SE, Ronavi SD | не кандидаты | нет класса OP-01 |

Этот набор закреплён интеграционным тестом `TestGoldenPalletMatching`.

## Воспроизводимость

Каждый прогон (`POST /projects/{id}/matching-runs`) сохраняет условия как JSON, версию каталога, версию правил и все проверки со значениями. Каталог после прогона можно менять: старый прогон читается как был (`GET /matching-runs/{id}`). Проект подбирает по снимку задачи; после правки задачи он показывает `dataChanged`, а `refresh-snapshot` берёт новые значения.
