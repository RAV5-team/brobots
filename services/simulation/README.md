# Шаг 3 «Симуляция»: проверка конфигурации из подбора

Шаг «Подбор» рассчитывает, **сколько роботов и зарядных станций нужно** складу.
Сервис симуляции прогоняет рабочий день именно этой конфигурации на
имитационной модели (SimPy) и отвечает:

- работает ли конфигурация;
- что докупить, чтобы работала;
- без чего можно обойтись, сохранив запас на рост объёма.

Результат — вердикт, изменение парка, обоснование и **предлагаемые поправки**
для следующих шагов. Какие поправки принять, решает пользователь, а хранит его
выбор и передаёт дальше платформа. Денег сервис не принимает и не считает:
экономику по принятым поправкам пересчитывает оркестратор через сервис
экономики.

## Запуск

Нужны Python 3.12 и PostgreSQL (у сервиса своя база). Адрес базы —
переменная окружения `DATABASE_URL`.

```bash
pip install -r requirements.txt
export DATABASE_URL=postgresql://simulation:…@localhost:5432/simulation

alembic upgrade head        # схема базы: один раз и после обновлений
python -m app.server        # API, экран шага и встроенные воркеры → http://localhost:8765
python -m app.worker        # отдельные воркеры (тогда серверу SIM_WORKERS=0)
```

Один Docker-образ выполняет все три роли:

```bash
docker build -t simulation .
docker run --rm -e DATABASE_URL=… simulation alembic upgrade head
docker run -d -p 8765:8765 -e DATABASE_URL=… simulation
docker run -d -e DATABASE_URL=… simulation python -m app.worker
```

Миграции — отдельный разовый шаг, при запуске сервера они не применяются.
Сервер и воркер при старте сверяют ревизию схемы и не запускаются, если она
не совпадает (код выхода 3; 2 — неверные настройки, 1 — база недоступна).

### Настройки

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `DATABASE_URL` | — (обязательна) | адрес базы сервиса |
| `PORT` | 8765 | порт HTTP |
| `SIM_WORKERS` | 1 | воркеров в процессе сервера; 0 — только API |
| `SIM_DB_POOL_MIN` / `SIM_DB_POOL_MAX` | 1 / 10 | размер пула соединений |
| `SIM_DB_POOL_TIMEOUT_S` | 5 | ожидание соединения; дольше — ответ 503 |
| `SIM_DB_CONNECT_WAIT_S` | 30 | ожидание базы при запуске |
| `SIM_POLL_INTERVAL_S` | 1 | пауза между проверками очереди |
| `SIM_HEARTBEAT_S` | 5 | как часто воркер подтверждает, что жив |
| `SIM_STALE_AFTER_S` | 60 | через сколько без подтверждения задание возвращается в очередь (больше трёх `SIM_HEARTBEAT_S`) |
| `OIDC_ISSUER` | — (обязательна серверу) | издатель токенов Keycloak: `${PUBLIC_URL}/auth/realms/rav5`, без `/` в конце |
| `OIDC_JWKS_URL` | — (обязательна серверу) | ключи Keycloak по внутреннему адресу |
| `OIDC_AUDIENCE` | — (обязательна серверу) | аудитория сервиса: `rav5-sim` |
| `INTERNAL_CALLER_AZP` | `rav5-api-internal` | клиент, которому открыты внутренние пути |

Воркеру (`python -m app.worker`) `OIDC_*` не нужны.

### Доступ

Токены проверяются по JWKS Keycloak (`adapters/auth/jwks.py`, зависимости FastAPI —
`adapters/web/auth.py`, правила — [docs/keycloak/middleware.md](../../docs/keycloak/middleware.md)).
`GET /`, `/index.html` и `/api/health` открыты всем; остальные пути — гостю (без
`Authorization`) или пользователю с токеном `aud rav5-sim`. Присланный токен обязан
быть валидным (401), сервисный токен здесь — 403. Ошибки доступа — `{"code", "message"}`.
Ключи загружаются в фоне; до первой загрузки `/api/health` отвечает 503.

Владение: задание, поставленное пользователем, записывается с его `sub`
(`jobs.owner_sub`); его ход, прогоны и трассы видит только он, для остальных
и для гостя — 404, как у несуществующего. Задание гостя владельца не имеет и
открыто любому, кто знает номер. Условие владения — в SQL-запросах
репозитория, двойник повторяет его, контрактный тест сверяет обе реализации.

## Экран шага

1. **Конфигурация из подбора** — решения «Подбора»: роботы, станции, пиковая
   потребность, производительность робота.
2. **Переход к симуляции** — что проверяем и как считал подбор; состав можно
   изменить вручную.
3. **Параметры симуляции** — форма `simulation_params` (до двух сценариев) с
   источником каждого значения; справа — потребность по часам и тело запроса.
4. **Запуск** — ход расчёта с журналом сервиса.
5. **Результат и рекомендация** — вердикт, обоснование, изменение парка и
   поправки. Кнопка «Учесть» запоминает выбор поправок на экране; в сервис он
   не отправляется.
6. **Графики и 2D** — почему столько роботов и станций, загрузка по часам,
   структура времени, два синхронных 2D-плеера «из подбора» и «рекомендация».

## HTTP API

Полное описание — [`docs/openapi.json`](docs/openapi.json) (OpenAPI 3.1), в
работающем сервисе — `GET /api/openapi.json`.

API — приложение FastAPI (`adapters/web/server.py`), сервер — uvicorn
(`app/server.py`). Контракт ведётся вручную в `adapters/web/openapi.py`:
автоматическая схема и `/docs` FastAPI отключены. Ошибки — `{"error", "errors"?}`,
в том числе 404 на неизвестный путь и 405 на неверный метод.

| Метод и путь | Назначение | Ответы |
|---|---|---|
| `GET /` | экран шага | 200 |
| `GET /api/health` | доступность базы и ревизия схемы (для healthcheck) | 200, 503 |
| `GET /api/meta` | справочники формы, примеры сценариев, демо-вход | 200 |
| `GET /api/openapi.json` | спецификация OpenAPI | 200 |
| `GET /api/simulations/schema` | JSON Schema запроса | 200 |
| `POST /api/simulations/preview` | потребность по часам и сверка со следом расчёта, без имитации | 200, 400, 413, 422 |
| `POST /api/simulations` | постановка проверки 1–2 сценариев в очередь | 202, 400, 413, 422, 503 |
| `GET /api/simulations/jobs/{job_id}` | ход задания, по готовности — прогоны | 200, 404, 503 |
| `GET /api/simulations/{simulation_id}` | прогон | 200, 404, 503 |
| `GET /api/simulations/{simulation_id}/traces` | трассы для 2D-плеера (gzip, если клиент принимает) | 200, 404, 503 |

Тело POST — JSON-объект; ошибки приходят в виде
`{"error": "…", "errors": [{"field": "…", "message": "…"}]}`: 400 — тело не
JSON, 413 — тело больше 1 МБ, 422 — тело не объект, ошибки входа по полям или
строки, которые PostgreSQL не примет (символ NUL, одиночные суррогаты), 503 —
база недоступна.

Задание (`GET /api/simulations/jobs/{job_id}`) содержит `job_id`, `status`
(`queued` / `running` / `done` / `error`), `log`, `elapsed` (от постановки в
очередь), `workers` — когда расчёт начался; при `done` — `simulation_ids` и
`runs`, при `error` — `error` и, если ошибка во входе, `errors`. Номера заданий
и прогонов — 32 шестнадцатеричных символа.

### Сценарий для оркестратора

```bash
# 1. запуск → 202 {"job_id": "…", "status_url": "/api/simulations/jobs/…"}
curl -s -X POST localhost:8765/api/simulations -H 'Content-Type: application/json' -d @request.json

# 2. опрос, пока status — "queued" или "running"; при "done" в ответе есть runs[]
curl -s localhost:8765/api/simulations/jobs/<job_id>
```

3. Пользователь выбирает поправки из `runs[].adjusted_input_set.items`; по
   умолчанию выбраны те, у которых `default_selected: true`.
4. Оркестратор сохраняет выбор и передаёт значения `simulated` выбранных
   поправок в пересчёт экономики.

## Запрос

```json
{
  "configuration": {
    "configuration_id": "cfg-dmr-carrier-p",
    "robot_count": 19,
    "charger_count": 5,
    "robot": {"name": "DMR Carrier P", "v_max": 1.5, "autonomy_h": 10, "charge_time_min": 90,
              "t_load_s": 60, "t_unload_s": 60, "width_mm": 1000},
    "calc": {"peak_trips_h": 129.5, "route_len_m": 100, "cycle_s": 342, "eff_prod": 8.0,
             "n_util": 0.8, "n_kv": 0.6, "n_avail": 0.95, "n_reserve": 0.15}
  },
  "location": {"active_area_m2": 10000, "aisle_main_m": 3.5, "aisle_rack_m": 2.8, "speed_limit_m_s": 1.5},
  "task": {"in_per_day": 1000, "out_per_day": 1000, "manual_share": 0.05, "peak_k": 1.5,
           "shift_start_h": 7, "shifts": 2, "shift_h": 11},
  "scenarios": [{
    "name": "Разнесённые пики, много людей",
    "simulation_params": {
      "schedule":        {"peaks": [{"flow": "in", "start_h": 8, "dur_h": 3}, {"flow": "out", "start_h": 14, "dur_h": 3}]},
      "service":         {"wait_limit_min": 15, "on_time_target": 0.95},
      "growth":          0.2,
      "site_conditions": {"traffic": "high", "abc": "none", "mttr_h": 2},
      "verification":    {"tolerance": 0.10, "fleet_policy": "add_and_reduce", "design_volume": "current"}
    }
  }]
}
```

- **`configuration`** — выбранная конфигурация. Обязательны `robot_count`,
  `charger_count`, паспорт робота (`v_max`, `autonomy_h`, `charge_time_min`,
  `t_load_s`, `t_unload_s`, `width_mm`) и след расчёта `calc`: `peak_trips_h`,
  `route_len_m`, `eff_prod`, `n_util`, `n_kv`, `n_avail`, `n_reserve` и время
  цикла (`cycle_s` или `cycles_h`). От следа зависят вердикт и поправки,
  поэтому значений по умолчанию для него нет. Необязательно `avg_trips_h` —
  для сверки с задачей.
- **`location`** — площадка; без полей берутся значения склада из датасета.
- **`task`** — задача проекта: объёмы и режим смен. Это значения по умолчанию
  для параметров сценария.
- **`scenarios`** — один или два сценария вида
  `{"name", "simulation_params"}`. Любое поле `simulation_params` можно
  опустить: режим смен, пик и объёмы берутся из `task`, остальное — по
  умолчанию. Поля сценария вне `simulation_params` — ошибка 422.

Контракт строгий: поле, которого нет в схеме, — ошибка 422 с путём
(`configuration.robot.robot_id: неизвестное поле`). Так опечатка в
необязательном поле не превращается молча в значение по умолчанию, а
денежные и служебные поля «Подбора» не уходят в сервис. Оркестратор передаёт
только поля контракта.

Значения из сценария и из задачи проверяются по одним правилам. Ошибка — 422
с путём до поля, например `scenarios[0].simulation_params.service.on_time_target`
или `scenarios[0].task.shifts`. Пики, которые не помещаются в рабочее окно при
заданном коэффициенте пика, — тоже 422 (`…simulation_params.schedule.peaks`),
в том числе в предпросмотре.

## Ответ: прогон сценария

| Поле | Что в нём |
|---|---|
| `status` | итог проверки (таблица ниже) |
| `fleet_change` | было → стало: роботы и станции |
| `verdict` | заголовок, пояснения, обоснование, риски — готовый текст для экрана |
| `checks_before`, `checks_after` | четыре условия вердикта до и после |
| `evidence` | кривая по числу роботов и строки по числу станций для обоснования |
| `kpis`, `kpis_before`, `hourly_before`, `hourly_after` | показатели и загрузка по часам |
| `adjusted_input_set` | предлагаемые поправки для следующих шагов |
| `resolved_params` | итоговое значение и источник каждого параметра: `user`, `task`, `default` |
| `warnings` | расхождения входа со следом расчёта и предупреждения о расписании |

| `status` | Значение |
|---|---|
| `confirmed` | работает, меньше нельзя |
| `can_reduce` | работает, можно меньше с сохранением запаса на рост |
| `needs_additions` | не работает, указано, что докупить |
| `layout_bottleneck` | не работает, роботы не помогают — узкие проезды или ворота |
| `not_achievable` | не работает даже с +15 роботами |

**Поправки** (`adjusted_input_set.items`):
- `robot_count`, `charger_count` — `override`, заменяют результат формулы
  подбора; выбраны по умолчанию, если состав изменился;
- `n_kv`, `n_util`, `n_avail`, `route_len_m`, `cycle_s`, `eff_prod` —
  `calibration`, измеренные коэффициенты; по умолчанию не выбраны, иначе парк
  будет пересчитан повторно.

## Правила

**Вердикт.** Конфигурация подтверждена, если выполнены все четыре условия:
1. В пиковые часы вывезено не меньше (1 − допуск) потребности — норматив 34,
   допуск по умолчанию 10 %.
2. Паллеты забраны не позже заданного срока в требуемой доле случаев в худший
   смоделированный день.
3. Все рейсы выполнены за сутки.
4. Нет разрядов АКБ в работе.

Каждый смоделированный день — отдельное зерно генератора случайных чисел;
решение принимается по худшему дню.

**Докупка** — если конфигурация не проходит. Поиск идёт только вверх: оценка
по недобору пропускной способности, роботы при станциях с запасом, затем
минимум станций не меньше исходного; итог подтверждается на 4 днях. Считается
на текущий объём, при `design_volume: growth` — на объём с ростом.

**Уменьшение** (`fleet_policy: add_and_reduce`) — только до состава, который
выполняет те же требования **при росте объёма** (по умолчанию +20 %). Резерв
`n_reserve` из подбора заменяется проверенным запасом на рост.
1. Роботы — от оценки по загрузке в пик, шагом в одного робота.
2. Станции снимаются по одной, пока парк выполняет те же требования; минимум —
   одна станция. Решение операционное, цены в нём не участвуют.
3. Итог подтверждается на 4 днях.

## Хранение и выполнение заданий

Всё хранится в PostgreSQL; схема — миграции Alembic (`migrations/`).

| Таблица | Что хранит |
|---|---|
| `jobs` | задания: статус, запрос и сценарии (jsonb), журнал хода, попытки, ошибки, владелец (`owner_sub`) |
| `runs` | прогоны сценариев: SimulationRun целиком (jsonb) и основные поля отдельно |
| `run_traces` | 2D-трассы: gzip компактного JSON, ~130 КБ на прогон |

Удаление мягкое: во всех таблицах есть `deleted_at`; помеченные строки API не
отдаёт (404), а задание, помеченное удалённым, скрывает свои прогоны и трассы.
Механизма удаления и срока хранения пока нет.

Очередь — таблица `jobs`: воркер забирает задание через
`FOR UPDATE SKIP LOCKED`, поэтому экземпляров сервиса и воркеров может быть
несколько. Сценарии считаются в дочерних процессах (параллельно по ядрам);
журнал и подтверждение «жив» пишутся в базу. Если воркер перестал
подтверждать дольше `SIM_STALE_AFTER_S`, задание возвращается в очередь;
после двух попыток — ошибка. Владение подтверждается токеном `lease`: он
растёт при каждом захвате и никогда не уменьшается, поэтому результат
опоздавшего воркера отбрасывается. Счётчик попыток `attempts` — отдельный: он
ограничивает только повторы после сбоев, а штатная остановка (задание
возвращается в очередь, расчёт прерывается) попытку не тратит. Прогоны,
трассы и статус `done` сохраняются одной транзакцией.

Проверка одного сценария с поиском уменьшения или докупки и записью 2D-трасс
занимает на машине разработки 14–18 с.

## Структура

Гексагональная архитектура (порты и адаптеры). Зависимости направлены внутрь:
адаптеры знают о прикладном слое, прикладной слой — о домене, домен — ни о
ком. Конкретные адаптеры связывает только корень сборки `app/`.

```
simcore/       домен: имитационная модель, вердикт, поправки
application/   сценарии использования и порты (typing.Protocol)
adapters/      веб, воркер (входящие); PostgreSQL, процессы (исходящие)
app/           корень сборки: настройки, связывание, точки входа
```

| Путь | Роль |
|---|---|
| `simcore/verify.py` | вердикт, докупка, уменьшение, обоснование — SimulationRun |
| `simcore/inputs.py` | разбор и проверка запроса, правила полей, сверка со следом расчёта |
| `simcore/sim_params.py` | параметры шага `simulation_params`: поля, диапазоны, источники значений |
| `simcore/adjustments.py` | поправки для следующих шагов |
| `simcore/verdict_text.py`, `simcore/text.py` | тексты вердикта |
| `simcore/evaluate.py` | оценка состава по дням с кэшем прогонов |
| `simcore/engine.py`, `layout.py`, `demand.py`, `schedule.py`, `metrics.py`, `models.py` | имитационная модель и измерения |
| `simcore/viz.py` | 2D-трассы для плеера экрана |
| `simcore/version.py` | версия модели имитации |
| `application/submit.py` | постановка проверки в очередь: проверка входа до записи |
| `application/preview.py` | предпросмотр потребности без имитации |
| `application/process_job.py` | выполнение задания: подтверждения, ограждение `lease`, итог |
| `application/ports.py`, `models.py`, `errors.py` | порты, данные между слоями, ошибки |
| `application/input_policy.py` | строки, которые хранилище не примет |
| `adapters/web/` | HTTP API на FastAPI (`server.py`), тела ответов, OpenAPI и JSON Schema, демо-вход, экран (`static/index.html`) |
| `adapters/worker/loop.py` | потоки воркеров: опрос очереди, возврат зависших заданий |
| `adapters/postgres/` | пул соединений и репозиторий заданий (весь SQL) |
| `adapters/processes/` | расчёт сценариев в дочерних процессах |
| `adapters/json_codec.py` | JSON без NaN, gzip трасс |
| `app/runtime.py` | запуск, проверка схемы, связывание слоёв |
| `app/server.py`, `app/worker.py` | точки входа `python -m app.server` (uvicorn) и `python -m app.worker` |
| `app/config.py` | настройки из окружения |
| `migrations/`, `alembic.ini` | миграции схемы базы |
| `gen_docs.py` | перегенерация `docs/openapi.json` |
| `docs/openapi.json` | контракт сервиса, включая схему запроса (генерируется из кода) |
| `tests/` | тесты сценариев на двойниках (`fakes.py`), адаптеров, HTTP API и архитектуры |

## Разработка

```bash
# тестовая база (имя обязано содержать «test»: таблицы очищаются)
docker run -d --name sim-test-pg -e POSTGRES_USER=sim -e POSTGRES_PASSWORD=sim \
    -e POSTGRES_DB=simulation_test -p 55433:5432 postgres:17-alpine
export TEST_DATABASE_URL=postgresql://sim:sim@127.0.0.1:55433/simulation_test

pytest --cov                   # тесты и покрытие (порог 80 %)
python gen_docs.py             # после изменения контракта: обновить docs/openapi.json
pyink .                        # формат: 80 колонок
isort .                        # порядок импортов (профиль google)
pylint --rcfile=pylintrc simcore application adapters app migrations tests *.py
mypy simcore application adapters app migrations gen_docs.py
```

Тесты с базой (метка `db`) без `TEST_DATABASE_URL` пропускаются; в CI задайте
`SIM_REQUIRE_DB=1`, чтобы отсутствие базы роняло прогон. Домен и сценарии
тестируются без базы: сценарии — на двойниках портов из `tests/fakes.py`, а
контрактный тест прогоняет одни и те же проверки очереди на двойнике и на
PostgreSQL, чтобы они не расходились. Двойники живут только в тестах: режима
хранения в памяти у сервиса нет. Архитектурный тест следит за направлением
зависимостей: домен не импортирует ввод-вывод, прикладной слой — ничего кроме
домена, адаптеры не знают друг о друге, конкретные адаптеры связывает только
`app/`.

Код следует [Google Python Style Guide](https://google.github.io/styleguide/pyguide.html);
`pylintrc` — конфигурация Google без правок, настройки инструментов — в
`pyproject.toml`. Тест сверяет `docs/openapi.json` с кодом: если контракт
изменился, а `gen_docs.py` не запускали, тесты упадут.

## Ограничения

- Схема склада синтетическая: строится по площади и ширине проездов.
- Хранилище растёт без ограничений: удаления и срока хранения пока нет
  (~300 КБ на задание из двух сценариев вместе с трассами).
- Результат — предварительная оценка; скорость с паллетой и помехи от людей
  стоит проверить на пилоте.
